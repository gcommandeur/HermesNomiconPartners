## Pflicht bei JEDER Aufgabe (alte Fassung vor der Umstellung)

Das ist die **Memory-Datei** des Projekts. Sie enthaelt jede Aenderung, jede Aufgabe und jede Information, die der Nutzer von einer Sitzung bekommen hat - damit jede Sitzung (Laptop oder Cloud) exakt weiss, was passiert ist.

1. **Es gibt nur zwei Branches: `entwicklung` (Arbeit) und `main` (Live).** Keine weiteren Branches anlegen (auch keine `claude/...`), beide Sitzungen arbeiten und pushen auf `entwicklung`; nach `main` geht NIE etwas ohne das ausdrueckliche gruene Licht des Nutzers (Regel vom 2026-10-04, gilt fuer jeden einzelnen Merge).
   Arbeits-Branch ist `entwicklung`, nicht `main`. Beide Sitzungen arbeiten und pushen dort. Direkt auf `main` pusht niemand (in `.claude/settings.json` gesperrt); `main` deployt nach DigitalOcean und wird nur per Pull Request von `entwicklung` aktualisiert, nach gruener CI und auf Freigabe des Nutzers.
2. **Vor dem Start, immer in dieser Reihenfolge:** `git fetch`, auf `entwicklung` wechseln, `git pull --rebase origin entwicklung`, dann **diese Datei und `CLAUDE.md` lesen**. Erst danach arbeiten. Ist `main` weiter als `entwicklung` (z.B. nach einem Merge), `origin/main` in `entwicklung` mergen.
3. **Am Ende aktualisieren, im selben Commit wie die Aufgabe:**
   - einen Eintrag oben im **Protokoll** (neueste zuerst): Datum, wer (`Laptop` oder `Cloud`), was, Commits, was NICHT geprueft wurde, und **`Gemeldet:`** - die Kernaussagen, die der Nutzer in dieser Aufgabe zu hoeren bekommen hat (Ergebnis, Entscheidungen, offene Fragen, Empfehlungen);
   - **Offene Punkte** pflegen (Erledigtes entfernen, Neues ergaenzen);
   - neue **Entscheidungen** und **Stolperfallen** festhalten, sobald sie anfallen.
   - **Lokaler Branch `main` = `entwicklung` (Regel des Nutzers vom 2026-10-04, gilt ohne Rueckfrage):** Nach jeder Aufgabe, nach dem Push auf `entwicklung`, setzt die Sitzung den LOKALEN Branch `main` auf `entwicklung` (`git branch -f main entwicklung`, ohne den Branch auszuchecken). Das ist rein lokal und deployt nichts. **Ausdruecklich NICHT von der Regel gedeckt:** `origin/main` (GitHub, deployt nach DigitalOcean) - dorthin geht weiterhin nur mit dem gruenen Licht des Nutzers per Pull Request.
4. **Sofort pushen** (`git pull --rebase origin entwicklung`, dann `git push origin entwicklung`), damit die andere Sitzung den Stand sieht. Bei Konflikten in dieser Datei beide Eintraege behalten (Protokoll nach Datum ordnen), nie einen verwerfen.
5. Nichts Geheimes eintragen (keine Passwoerter, Tokens, Verbindungs-Strings, Kunden-/Kandidatendaten).
6. Eine Aufgabe ist erst fertig, wenn Tests/Pruefungen gruen sind, die **CI bei GitHub gruen** ist und diese Datei stimmt.
7. **Nach `main` bringen** (nur auf Freigabe des Nutzers): Pull Request `entwicklung` -> `main`, CI abwarten, mit **Merge-Commit** mergen (`gh pr merge --merge`, NICHT mehr `--rebase`, ohne `--delete-branch`: `entwicklung` bleibt bestehen), danach `entwicklung` wieder auf `main` bringen (`git merge origin/main`). Grund: Ein Rebase-Merge schreibt die Commits neu; die Kopie fuer die zweite Firma (`HermesNomiconPartners`) holt per `git merge upstream/main` und bekaeme dieselben Aenderungen sonst als verschiedene Commits (Konflikte). Mit Merge-Commit bleiben die Commit-Nummern gleich.

## Stolperfallen (alte Fassung vor der Umstellung)

- **Tests mit `client`-Fixture:** es legt beim Start eine `AuthSession` an; Tests, die "keine neue Session" pruefen, muessen das einrechnen (`FIXTURE_SESSIONS = 1` in `test_microsoft_login.py`). Gleichnamige Testdateien in `tests/api` und `tests/services` kollidieren (kein `__init__.py`) - Dateien eindeutig benennen.
- **Windows/lokal:** `python` ist der Store-Platzhalter und haengt - immer `backend/.venv/Scripts/python.exe`; pnpm per `corepack pnpm`. Viele Dateien haben CRLF-Zeilenenden - Skript-Edits muessen das beachten (das Edit-Werkzeug erledigt das).
- **CI weicht von lokal ab** (Python 3.12 und andere mypy-/SQLAlchemy-Typen): ein lokal gruener Lauf garantiert keine gruene CI. Nach jedem Push `gh run list` pruefen.
- **Tests:** keine festen Datumswerte (Zeitbomben); Test-Payloads muessen gueltig sein - ein ungueltiger (422) macht den Test wirkungslos (kam zweimal vor); zuerst pruefen, dass das Setup ueberhaupt Treffer erzeugt.
- **Neue Routen mit `submission_id`/`placement_id`/`fee_id` im Pfad** brauchen `SubmissionAccess`/`PlacementAccess`/`FeeAccess`.
- **Migrationen** immer auf einer Kopie der lokalen DB upgrade, downgrade, upgrade testen. Aktueller Head: `c1f5a9b3d7e8`.
- **Buttons ignorieren Tailwind-Schrift:** `globals.css` setzt `button,input,select,textarea{font:inherit}` ohne Layer; `text-[..]`/`font-*` an einem `<button>` wirken deshalb nicht (Utilities liegen im Layer). Mit `!` am Utility (`text-xs!`) oder ein Kind-Element mit der Klasse benutzen.
- **Frontend: nie `pnpm build` ausfuehren, waehrend `pnpm dev` laeuft** - beide schreiben nach `frontend/.next`, danach laedt die Seite ohne Stile. Dev-Server stoppen, `.next` loeschen, neu starten.
- **Harmlose Git-Meldung:** `failed to delete '.git/worktrees/charming-mendeleev-84844e'` (toter Worktree-Eintrag auf dem alten OneDrive-Pfad) - ignorieren.
- **Verbotene Pfade/Orte:** Projekt nie zurueck in einen OneDrive-Ordner; nie Zugangsdaten committen; Ordner `.git-korrupt-backup/`, `backend/data/lukas_postfach_import/`, `backend/scripts/full_dry_run_log.txt` gehoeren nicht ins Repo.
